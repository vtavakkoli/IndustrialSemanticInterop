# Reproducibility Guide

This repository is designed so benchmark runs can be reproduced from a pinned Git commit and an explicit configuration file. For publication-facing results, preserve both the **raw outputs** and enough environment metadata to reconstruct the run.

## Recommended path: Docker

The repository's Docker image uses Python 3.12 and installs dependencies from `requirements.txt` before running the benchmark.

```bash
docker compose up --build
```

`docker-compose.yml` mounts the local `results/` directory into the container so generated artifacts persist on the host.

For a clean reproduction, record:

```bash
git rev-parse HEAD
docker --version
docker compose version
```

and archive the configuration file used for the run.

## Native Python workflow

### Linux / macOS

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
python -m scripts.run_all
```

### Windows PowerShell

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
$env:PYTHONPATH = "."
python -m scripts.run_all
```

## Direct benchmark execution

Run the default framework configuration:

```bash
python -m framework_benchmark run --config configs/default.yaml
```

Use the smaller configuration for a quick smoke run:

```bash
python -m framework_benchmark run --config configs/minimal.yaml
```

## Default deterministic settings

The main configuration currently defines:

- `repetitions: 20`
- `seed: 4242`
- 5 interoperability strategies
- 6 selection policies
- 3 scale levels
- 4 security modes
- 10 fault / constraint flags

Do not change the seed, scenario semantics, or aggregation rules silently when comparing with previously generated results.

## Test the code before a benchmark run

```bash
pytest -q
```

A passing test suite does not validate the scientific conclusions by itself, but it helps establish that adapters, scenario handling, metrics, analysis, and report-generation behavior remain internally consistent.

## Output preservation

Depending on the workflow, generated artifacts are stored below `results/`, including:

- `raw_runs/`
- `ablations/`
- `robustness/`
- `aggregated/`
- `figures/`
- `final_report.html`
- `final_report.md` when generated by the selected pipeline

For publication or external review, preserve the raw runs used to produce every reported aggregate or figure.

## Minimum run manifest

A reproducible experiment record should include at least:

```text
repository: vtavakkoli/IndustrialSemanticInterop
commit_sha: <git commit>
configuration: configs/default.yaml
seed: 4242
repetitions: 20
python_or_container: <version/image>
host_os: <OS and version>
hardware: <CPU / memory, and virtualization details if relevant>
command: <exact command>
run_timestamp_utc: <timestamp>
raw_output_location: <path or artifact identifier>
```

If hardware or virtualization differs between studies, report that explicitly because latency, throughput, and resource measurements may not be directly comparable across hosts.

## Result validation checklist

Before treating a result as publication-ready:

- [ ] Record the exact Git commit SHA.
- [ ] Record the exact configuration file.
- [ ] Preserve seed and repetition count.
- [ ] Run `pytest -q` on the evaluated commit.
- [ ] Preserve raw run outputs.
- [ ] Record Python/container and host details.
- [ ] Confirm compared methods used identical scenario conditions.
- [ ] Regenerate aggregates and figures from the preserved raw data.
- [ ] Review results against `docs/paper_claim_boundary.md`.
- [ ] Avoid standards-compliance claims not supported by the implementation.

## Scientific caveats

The current benchmark is executed in a virtualized testbed and does not provide hardware-in-the-loop validation. Protocol-related adapters are representative / standards-informed research components rather than complete certified implementations. Reproducing a numerical result therefore reproduces behavior within the stated benchmark environment; it does not establish production interoperability or standards certification.

For the experiment definition and reporting rules, see [`benchmark_protocol.md`](benchmark_protocol.md).
